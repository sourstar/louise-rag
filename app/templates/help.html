What this is

In short: your node turns document collections into something you can search and ask questions about — and exchanges the expensive part (embeddings) with other nodes, checking everything it receives.

     corpus sources                              other peers
 (Gutenberg, NCBI, dumps…)                  ┌────────┐ ┌────────┐
          │                                 │ peer B │ │ peer C │
          │ fetch (profiles,                └───┬────┘ └───┬────┘
          │  licenses, mirrors)                 │          │

┌── THIS NODE ─────────────────────┐    corpus torrents · genesis

│  worker: discover → rdf → fts    │◄───────────┴──────────►
│              → embed             │

│     ▼                  ▼         │   vectors, (planned) signed
│  SQLite manifest    LanceDB      │   corpus enumeration —
│  (state, FTS)       (vectors)    │   verified, never trusted.
│     ▲                  ▲         │   stays local: state, FTS
│     │                  │         │   index — recomputed here

│  LLM for answers                 │

louise-rag is a peer-to-peer RAG platform: each node ingests document collections (Project Gutenberg, PubMed, …), indexes them lexically (tantivy FTS) and densely (embeddings in LanceDB), and answers questions over them with a local LLM. Nodes can exchange signed vector bundles so one node's GPU-hours serve many — with cryptographic verification instead of trust. Two processes run per node: the web process (this UI, the JSON API, the OpenAI-compatible endpoint) and the worker (ingestion pipeline). Both operate on the same SQLite manifest and Lance vector store; state never travels, vectors do.

Reading the screens

The pages show numbers and state; the explanations live here. If a reading is not obvious, it is described below rather than in a tooltip.

Node modes

modewhat runs

One node-wide setting, not per-collection: per-collection embed modes are untouched by all of these, so returning to run everything restores exactly what each collection was doing. Rescan all collections is greyed out in pause and seeding-only because the worker returns at the pause gate before it services discovery requests — a rescan would sit queued until the node runs.

A collection's counters

  • Counts are cached for two minutes and refreshed in the background. Each is a full scan of that collection's documents table — about 12 s on pubmed's 24M rows — so computing them per page load made the page a 20-second wait. A backfill moves over days; a two-minute-old count does not mislead.
  • counting means the first counter scan since a restart is still running (~25 s on the largest manifests). The bars read 0 until it lands.
  • The (…) beside a stage is how long the rest will take, from the rate measured over the last few minutes. It is the proof a stage is moving when the bar barely shows it. Hover it — the tooltip always says where the figure came from, or why there isn't one.
  • (-) means work remains and there is no rate worth quoting yet. Three things it can be, and the tooltip says which: no rate yet (nothing measured since this collection last changed), one window so far (measured once, waiting for a second before showing a number that might be revised tenfold), or no progress in the last 30 minutes. It is never an error.
  • Nothing at all beside a stage means there is nothing left for it to do — either it is finished, or the only documents left are blocked and waiting for you.
  • waiting for the index on the parsed row is not a stall: parsing has run ahead, the worker gives the thread to indexing while a full batch is ready, and parsing resumes when indexing catches up. The tooltip says how far ahead it is.
  • An estimate takes a few minutes to appear, and the clock only runs while this page is open: the rate is sampled when the Library is rendered, so two views at least five minutes apart are needed before the first figure — and a restart, or anything that resets a counter, starts that stage over.
  • blocked counts documents that failed a stage or exhausted their retries. No stage picks them up again — which is why the bars stop short — until clear errors & retry.
  • not indexable is a corpus fact, not a failure: the source has no usable content for those documents (no text, or retracted upstream). Retrying cannot change it, and the next scan re-applies it, so they are counted separately.
  • embedding paused means the backend gate stopped this collection's encoder writes; the reason beside it names the mismatch. See Embedding safety below.
  • Label colour throughout: green = complete, turquoise = running or in the scheduling pool, orange = on-demand only, grey = off or paused.

Pre-embedded archives

  • The vector archive is its own download, separate from the corpus and behind it — without the corpus the vectors are useless. Each file applies as soon as it lands for the documents already indexed, is revisited as more clear indexing, and is deleted once nothing in its range still waits.
  • REJECTED means the archive was not produced by this collection's encoder. Correct the [embed] recipe, then genesis retry <collection> puts it back in line.
  • Individual files can fail the same-function check while the rest imports normally; those id ranges simply fall to the local encoder.
  • A collection with acquisition off does not fetch its vector archive either — the archive follows the same acquisition switch and the same licence gate as the corpus.
  • pre-embedded (dense) is counted over the archive's declared id range (MedCPT: PMIDs 0–36,999,999): in-scope documents inside it that hold vectors, over every in-scope document inside it. It counts vectors held, not the import ledger. The ledger counts, per archive file, the documents that file has delivered, each once; it does not drop one the local encoder later re-embeds, and rows counted before 2026-09-14 lost the flushes of any pass cut short — louise genesis recount recomputes them from the documents' provenance. Under embed = "all" some of the vectors held can be the local encoder's — nothing records per document which. A gap inside the range is named on the card, split into documents still being indexed and documents past indexing; for the latter, louise health says whether the archive is still serving them. Documents outside the range — past its end, and any in a gap between its files or with an id that is not a number — get nothing from the archive: only the local encoder can embed them, so under off they wait. An archive that declares no coverage shows the ledger's count. A document the archive turns out not to hold (no abstract, a chunk-shape mismatch) is released to the local encoder once its archive file is complete.

Ask, and the reader

  • Pinned facts are not search results. Entity lookups appear as their own blocks above the ranked hits: they are never ranked, never fused with passages, and carry no [n] citation.
  • Annotations consulted is the second chip row: one chip per annotations collection held here (02 §2.10), named with the collection it annotates. On, its work claims group a work's editions into one hit ("also in:") and its claims appear beside each hit ("also:"); off, the search runs as if the node did not hold it. An annotations collection is never a search leg of its own. Both chip rows are remembered in this browser between searches: a collection turned off stays off until turned on again, a new one starts on.
  • Show results in … translates with the node's own local model, not an external service: the translation model (MADLAD-400, TRANSLATE_URL) where the node has one — about a second for a question into every main language, six for a whole entry — else the chat model, which takes minutes for a page. Titles and headings come first, then the answer, then the entries by rank.
  • A language limit is read from the question by the same model and taken only when the words it names are really in the question and are not the whole of it — so "German history of whaling" is a topic, never a limit. When a limit you wrote was not taken, write lang:de, which is never guessed.
  • No hits usually means the lexical index has not been built for the languages currently in scope — check the collection's indexed (lexical) stage and the scope languages before suspecting the query.
  • The reader shows a header and nothing else when a document has not passed the fts stage: it renders only what the index stores hold. It never falls back to the raw corpus file, because opening one container to reach a single document costs ~15 s on a PubMed xml.gz.

System

An endpoint that pings unreachable does not break search: dense retrieval degrades gracefully and lexical search is unaffected. The health table is a liveness indicator only — no pipeline decision consults it.

The GPU panel. The bar says whose the card's memory is: Louise's models, LocalAI's other models, what is outside LocalAI's models (other processes, the driver's own buffers); the rest is free. Without LocalAI's figures it says what the processes shown hold and what the driver counts and no process shown holds. Each row then gives three host figures, and only two of them are occupancy: GPU buffers in host RAM and process RAM are real; mapped file is page cache seen through the process (the model file, right after a load), which the kernel takes back whenever it wants the room. A row marked pushed off the card has most of its buffers in host RAM: the card was overcommitted and the driver moved them out, silently.

Ingestion pipeline

In short: every document climbs four steps — found, described, searchable, embedded — and any step can be safely interrupted and re-run.

Per document, in order: discover (corpus scan; also at startup and every DISCOVER_INTERVAL_MIN) → rdf (metadata) → fts (chunking, lexical index, entity tagging) → embed (dense vectors, when the embed mode says so). Every write is delete-then-insert keyed on the document uid, so any stage can be interrupted and re-run safely; a worker stop (SIGTERM) finishes the current document, commits, and exits cleanly. Each stage carries a version (CHUNK_VERSION, FTS_VERSION, ENTITY_VERSION, EMBED_VERSION); bumping one re-processes exactly the documents behind it — never silently.

Scope & embed modes

In short: scope decides which documents are in play; embed mode decides how much encoder time they get.

The scope (languages, explicit ids, caps) decides which documents are in play. The embed mode decides encoder spending: off — never embed; on-demand — embed only what queries actually touch (a priority queue fed by search misses; stored as "lazy" in the TOML and API, kept for compatibility); all ("all local") — background-backfill everything in scope, whoever leads a part, its duplicates becoming checks; all p2p (stored as "p2p") — embed only the parts rendezvous gives this node among the live peers (04 §4.5) and publish as it goes: the worker's publisher bundles and announces each part as its vectors complete, every five minutes, for every shared collection whatever its mode — so all p2p needs sharing on, and the Library asks before writing either. The priority queue always outranks the backfill, so a user-requested document embeds first. Set the mode via the collection's drop-down (written to its file) or POST /api/scope (see HTTP API).

What the mode actually controls

The knob touches one thing only: local encoder spending on dense vectors. Fetching, parsing and indexing never depend on it — they follow the node-wide worker state. Archive import (pre-embedded data) never depends on it either — it runs whenever the worker runs.

operationoffon-demand / fix on demandall / fix
fetched (acquisition) runs regardless — governed only by the node-wide worker state (run everything and download only fetch; pause stops it)
parsed (rdf) runs regardless under run everything; stands down under download only and pause
indexed (lexical) same as parsed — never gated by the embed mode
embedded (dense) — no archive never embeds; documents stay without vectors embeds only documents queries actually touch (the priority queue); no background work background-backfills everything in scope, queue first
embedded (dense) — pre-embedded archive declared the archive imports anyway (it is free); what it cannot cover stays without vectors (and post-quarantine re-embeds never run) the archive imports anyway; the encoder embeds only what a query touches the archive imports anyway and goes first; the encoder background-embeds only the documents the archive cannot cover — outside its declared id ranges, or left uncovered once an archive file is complete

The Library's embed-mode control is persistent: it writes embed_mode = "off" | "lazy" | "all" into collections/<name>.toml (Tier-2 desired state, the same way collection-create and the license ack write it) and applies immediately — it survives restarts. A runtime-only override is still possible via POST /api/scope; that one lasts until the worker next applies the TOML. A collection whose TOML is silent defaults to on-demand (stored value lazy). A collection with a pre-embedded archive has the same knob with the same three values — one knob, not two. The archive imports in every mode (it costs no encoder time and always goes first); the mode says what the local encoder does with the rest. Under all it embeds only what the archive cannot cover: documents outside the archive's declared id ranges (PubMed articles newer than the MedCPT snapshot, ~3M of 40M) and, once an archive file is complete, the few inside its range the archive did not hold (no abstract, a chunk-shape mismatch). Until that file is complete those wait for it — never a duplicate, never a wrong import. off leaves the uncovered documents without dense vectors — and note that after a quarantine, off also means the affected documents are never re-embedded.

Node-wide, the Library page offers three modes. run everything is the normal state. download only keeps acquisition and discovery going while parse, index and embed stand down — the two halves cost very differently, and this is the switch for when the node's heat or CPU matters more than its progress. Per-collection embed modes are left untouched, so switching back restores exactly what each collection was doing. pause stops everything, including starting new fetches.

Each Library card names which processor that spending lands on — GPU for a collection served by the shared GPU encoder (one collection at a time, serial by design) and CPU for one served by a CPU encoder container, which runs beside the GPU without competing for it. Declare it explicitly with device = "gpu"|"cpu" in the collection's [embed] block; otherwise it is inferred from concurrency. The device is descriptive only and never part of the embedding space — the same model on a different device computes the same function.

Under all, the card reports the dense backfill still awaiting the encoder rather than the on-demand queue, which is empty by definition in that mode: backfill selects straight from the manifest and never touches the queue.

Embedding safety

In short: two vectors are only comparable when the exact same machinery produced them — everything in this section defends that one rule.

Vectors are only comparable inside one embedding space: same model weights, dtype, normalization, pooling, chunking and cleaning versions. The space is pinned per collection at first boot and checked on every boot — a confirmed mismatch refuses to boot rather than silently mixing spaces.

Because an HTTP embedding endpoint can change behind a stable name, the worker additionally runs a behavioral backend gate: on first use it embeds fixed probe texts and records the vectors; before writing any new vectors it re-embeds the probes and requires cosine ≥ 0.995 against that baseline. If the endpoint stops reproducing itself (model swap, build change, pooling change), embedding pauses — documents are never marked errored, search and lexical indexing continue — until an operator fixes the endpoint or accepts the new backend by removing its baseline file, which the next check records afresh (which implies re-embedding).

EMBED_BATCH=1 is load-bearing. llama-server corrupts long sequences when a single embeddings request carries multiple texts (verified live 2026-08-17: batch-of-8 → cosine 0.32 against the same text embedded alone), and its prompt cache can replay corrupted results afterwards. Parallel single-text requests are verified safe — use EMBED_CONCURRENCY for throughput, never EMBED_BATCH. Also pin the embedding server's image by digest: a moving tag is how a backend changes identity silently.

Bundles & the P2P plane

In short: nodes share finished embeddings so one GPU serves many — and every import is checked, never trusted.

A bundle is a signed, portable set of vectors: header + Parquet vectors + per-document possession hashes, Ed25519-signed by the producing node's key. Importing one lets a document reach embedded without local GPU work. Every import passes admission checks regardless of who signed it (structure, isotropy, chunk-overlap invariant, sample re-embedding, degenerate-vector detection), producer keys denied or burned on the trust list (louise hold key trust) are refused, and imported chunks can be verified on use — each verification is permanent per chunk. The verification ladder (T0 structural → T3 spot recompute against the local model) records evidence for every decision, and louise hold vectors check re-checks a sample of what is held.

What travels, what stays local

The dividing rule: a peer shares what is expensive to make and cheap to verify, and recomputes what is the reverse.

artifacttravels?why
corpus bytesyes (torrents, mirrors) expensive to move from origin, trivially verified by hash.
vectorsyes (signed bundles, genesis archives) the GPU-hours are the whole cost; verifiable by sampled re-embedding against the local encoder.
corpus enumeration (which documents exist in a snapshot)designed, not built discovery over millions of files is slow and every peer repeats it identically — a signed listing in the snapshot manifest would let a peer skip it and still verify what lands. The plan is recorded; no wire format exists yet.
FTS indexno — deliberately cheap to recompute locally (~1 ms/doc), expensive to verify received (the only check is rebuilding it, which costs the recompute anyway), and coupled to local versions and config — a shared index would import another node's chunking decisions unverifiably.
SQLite state (manifest, progress, settings) never it describes this node's pipeline position and choices; on any other node it is meaningless or wrong.
extra formats (e.g. epubs)never local convenience only — peers exchange the data that fulfils Louise's purpose (see Acquisition → Extra formats).

Reusing published embeddings (genesis import)

In short: when someone already paid the GPU-hours for a corpus, this node reuses their vectors — after checking they came from the same encoder.

If someone already paid the GPU-hours for a corpus, this node reuses that work instead of re-embedding: NCBI publishes MedCPT vectors for essentially all of PubMed (public domain), and any third party can publish a compatible dataset. The import is admission, not trust: only documents this node actually holds receive vectors; every vector is converted (f32→f16, L2-normalized) on the way in; and a sample is re-encoded through the collection's own [embed] endpoint — if the archive was not produced by the same function, the shard is refused whole, however well-formed. Provenance is ledgered per shard, imports resume mid-archive, and the worker gap-fills whatever the archive lacks (newer documents) through the same endpoint, so the space stays coherent forever.

Default-on. A collection whose TOML declares genesis_archive = "medcpt-pubmed" (written automatically by the create dialog when the plugin has a known archive; delete the line to opt out) is drained by the worker on its own — one shard per round, before any local GPU embedding — and the Library card shows the coverage over the archive's declared id range, and how many documents lie past it. An archive is split by its producer into numbered archive files ("shards": NCBI publishes MedCPT's vectors as 37 files of ~3 GB; the pre-embedded Wikipedia corpus IS its 1,447 parquet files). A remote archive is a second download stream of the collection, beside the corpus fetch and behind it on the link (the corpus wins: without it the vectors are useless — that is the archive class of the bandwidth budget). Files land a few at a time (a bounded cache on disk, GENESIS_CACHE_BYTES, and a disk preflight), and each one applies as soon as it lands for the documents already indexed, is revisited as more of them clear indexing (a revisit that finds nothing backs off, per file), and is deleted once nothing in its id range still waits. MedCPT's files are exact PMID ranges (file i = PMIDs i·10⁶ …), so the worker knows from the id alone which documents the archive can cover — the local encoder never spends a GPU-hour on one. A local archive is read file by file as its documents pass indexing. The CLI does the same thing on demand:

Why some pre-embedded data is combined with a collection and some stands alone. The rule follows what the data is. Pre-embedded data that is a corpus in its own right — text and vectors together, like the wikivec parquet files — stands alone as its own collection, with its own documents, ids and embedding space. Pre-embedded data that is vectors for another collection's documents — MedCPT for pubmed: same document ids, no text of its own, computed in the very space the collection is pinned to — must live inside that collection, shown as the light-green sub-box on its Library card. Split out, it would be a "collection" owning vectors but no documents: it could not search lexically, could not verify possession (hashes bind to document bytes it would not have), and retrieval would double-count the same documents across two fused legs. So: corpus-with-vectors → own card; vectors-for-your-documents → sub-box. 

# NCBI MedCPT vectors into the pubmed collection (resumable):
louise hold vectors import pubmed --archive medcpt-pubmed

louise hold vectors show <collection>     # coverage, producers

This cuts both ways: a collection filled from a genesis archive (or embedded locally) can be exported as a signed bundle from its Library card — publishing embeddings other nodes (and other projects) can verify and reuse is exactly how a platform earns visibility. The per-collection encoder setup for MedCPT (two small CPU containers) is documented in deploy/truenas-medcpt-embed.yaml.

Packs — the distribution format

In short: a pack is a corpus repackaged into exactly what the platform searches — parsed text, sliced by language or year, shard by shard — with a signed manifest, so any node can take the part it wants, check it against the origin, and run it with no origin files and no parser. The design is docs/pack-format.md.

What is in one. A directory: manifest.json (what the collection is: id, snapshot, slicing scheme, chunker layers, license, every shard with its hash — signed with the node key), validation.json (which checks to run), TERMS.txt (the license terms, byte-exact), and records/<slice>/NNNNN.jsonl.zst — the corpus as JSON Lines, one record per line, in independent zstd frames of 1,000 records with an index at the end. zstd -d shard.jsonl.zst | less prints the records: nothing in a pack needs our tools to be read. A slice is the human-facing part (Gutenberg lang=it, PubMed year=1975-1979, Wikipedia lang=de/pages=2M); a shard is the transfer unit inside it (~50 books, 30,000 abstracts, 2,000 articles), closed once written. Vectors and the text index are planned as separate members; today a node builds both itself from the records.

A pack is a closed snapshot. The procedure: the origin collection finishes fetching, parsing and indexing up to a cutoff date; the pack is built from it with louise hold records build <collection> --snapshot ID — records that existed at the origin on that date and nothing later (Gutenberg by release date, PubMed by DateRevised, Wikipedia by the dump's date; the rule is recorded in the manifest, and a resume under another cutoff is refused). Later content is an update: derived from the previous manifest and the origin by fixed rules, so two honest updaters produce the same bytes and there is nothing to reconcile (not built yet; see the design, §6.1).

Building one. From an existing collection: hold records build above (two passes over the collection's manifest — plan the slices, then write shards — resumable, state in DIR/.build/, logs one line per 30 s). From a raw corpus folder without a collection: python -m tools.pack_convert --plugin pubmed --corpus DIR --out DIR [--until DATE]. Only useful data enters a pack: parsed text and metadata, never epubs, XML markup or dump indexes. On the reference node packs live on their own datasets under /packs (PACK_MOUNTS_DIR).

Using one. The packed plugin, which served a pack as a collection, and pack adopt are boxed in attic/ until they are converted to the final format or dropped. The license is the origin's: a yellow-class pack carries the origin's terms text byte-exact, so the same acknowledgement (same sha256) covers corpus, pre-embeddings and pack.

Checking one. louise hold check <collection> [--checks roots,records,chunks,license,signature] [--sample 0.05] runs the pack's validation plan with platform code — every shard's bytes against the manifest's hashes, every record's content hash against its own text, re-chunking against the declared counts, the terms text byte-for-byte, the signature. Nothing shipped in a pack is ever executed. louise hold collection show, louise hold records show <collection> <uid> (one record and its chunks as JSON) and louise hold records show <collection> --shard <slice>/<n> (plain JSONL) are the inspection tools.

Sharing one. louise share <collection>, over a collection whose folder is a pack (none while the packed plugin is boxed), hashes one torrent per slice plus a small manifest member, all rooted at the pack, and publishes the torrent collection over them — a peer takes "PubMed before 1980" as the members of those slices (see Fetching from peers).

Chunker layers. A collection normally has one chunker. Where a pre-embedded archive fixed the chunking of the documents it covers and a better one is wanted for the rest (the "MedCPT case"), a collection may declare layers in its TOML — [[layers]] chunker = "verbatim" rule = "archive:<id>" … then [[layers]] chunker = "cdc" (the last is the default) — every document belongs to exactly one layer by that rule, all under one encoder. Declaring more than one layer changes the collection's space id (a new collection, louise hold collection derive); one layer changes nothing.

The vector index. Without one, every semantic query scans the whole vector table (13 s on 16 million rows, measured). The worker builds a local IVF index on its own once a collection's table holds VECTOR_INDEX_MIN_ROWS (100,000) rows — off the GPU loop, minutes to an hour on a large table, queries keep working meanwhile — and folds new rows in as they arrive. Search then probes a few buckets and re-ranks against the stored vectors (VECTOR_INDEX_NPROBES / VECTOR_INDEX_REFINE); the default type is ivf_pq (compact codes), ivf_flat keeps a full copy of the vectors for the best recall. index vector status|build <collection> shows or forces it. The index is local, built over the vectors a node holds; the pack design's shared bucket index is a later step.

Using every core. Parsing and chunking documents is pure Python, and all collections' pipelines share one interpreter — so the worker used one core however many it had. The parse pool (PARSE_PROCESSES, default cores−1) computes each batch's fetch/parse/chunk, metadata and pack records in low-priority child processes while the worker keeps every writer (index, vectors, manifest). Encoders, queries and the UI keep priority; set PARSE_PROCESSES=1 for the serial in-process path on a small node.

wikipedia Wikimedia's official multistream dumps, per wiki, optionally pinned to a dated snapshot. compressed containers (bz2 dump + index) — one article = one document, content-defined chunking (stable under edits). yellow (CC BY-SA; ack required) offers the wikivec sub-plugin at install (see below) — the offer is made once, at creation.
wikivec plugin id: embedded a published PRE-EMBEDDED corpus — today the Upstash Wikipedia 2024-06 / bge-m3 dataset: text and vectors travel together. parquet shards; one article = one document; the producer's chunk boundaries are preserved verbatim (that is what makes their vectors attach). yellow (content stays CC BY-SA; ack required) vectors are imported (genesis), not computed — dense search at zero GPU cost; the embed-mode knob only gap-fills what the archive cannot cover. The internal plugin id stays embedded: it is minted into every document uid and can never be renamed.

Adding a collection

In short: a collection is a Codex plus one small file saying what this node holds of it — hold collection create writes both.

1. Write a recipe. A TOML with every Codex field the plugin does not default: at least its [space] and [work] blocks, or --space-from a collection already held for the space (06 §6.6). The recipes under config/recipes/ are worked examples.

2. Create it. On the Library page, Add a collection: pick the plugin, paste the recipe, Create on this node. The same from a shell: 

louise hold collection create <plugin> --recipe FILE [--space-from <collection>]

The annotations type (02 §2.10) is in the same drop-down and takes no recipe: a name, the held collection it annotates with the target snapshot its claims hold from (prefilled with the one held now), an optional title, summary and annotator, and the claims file (JSON Lines, one claim per line). Check claims runs the check and writes nothing; Create runs the same check, refuses with the reason on a failing claim, and queues the create for the worker, which signs the first snapshot. Such a collection has no space and no encoder: it is held, checked and shared like any other, and its card in the Library shows what it annotates and how many claims it holds. 

louise hold collection create annotations --annotates <collection> --from-snapshot <id> --claims FILE --name <name> [--dry-run]

It embeds the calibration set with the encoder the recipe names, writes the Codex into the collection's SHARD, prints its id, and writes the collection's file, collections/<name>.toml (07 §7.8) — the file existing is the collection being held: 

codex  = "sha256:…"            # the collection this name holds, for its life
slices = []                    # "all" to fetch everything; nothing until you say so
kinds  = ["records", "vectors"]
embed  = "off"                 # off | on-demand | all: what this node spends
share  = false
# title = "…"                  # this node's own listing name, never published

[encoder]                      # REQUIRED: where this node reaches the Codex's encoder
url = "http://…"               # (+ query_url for a bi-encoder). There is no default:
                               # a file that names none is refused (System page)
embed_model = "…"              # REQUIRED: the model documents are embedded with
query_model = "…"              # REQUIRED: the model questions are embedded with (the same
                               # model named twice when one does both); on a model-container URL
                               # (…/upstream/<model>) each must be the model it names

[reranker]                     # optional: this node's reranker for this collection
url = "http://…/v1/rerank"     # the full endpoint; else RERANK_URL, else none
api = "jina"                   # jina ({query, documents}: llama.cpp) | tei ({query, texts})
rerank_model = "…"             # REQUIRED with the block: the body's model

Each collection's results are reranked by its own reranker, then fused by rank (05 §5.6). A reranker that is down, refuses, or exceeds platform.toml's [ask] latency_budget_ms (8000 by default) leaves that collection's results in their fused order, and the search says so (reranked: false).

Nothing else goes in the file. The plugin, layers, space, archive and pinned dump are the Codex's, and the origin files live at <LOUISE_ROOT>/collections/<name>/origin/ — the bytes may sit on other storage, mounted there. Files written before this shape still load; a rewrite keeps their older keys (profile, corpus_dir, …) only where they differ from what the Codex and the tree say.

3. Acknowledge, then fill it. A yellow- or red-class source is withheld from every use until louise hold collection ack <collection> records the acknowledgement. Then set slices = "all" in the file: the worker re-reads it between rounds and starts fetching, discovering and parsing — no restart. Origin files already on disk at the origin path are adopted, not fetched again.

Managing it. Each collection card also offers: export bundle — download this collection's vectors as a signed bundle (tar.gz) another node can import; import bundle… — upload a bundle into the collection's inbox, where the worker verifies and imports it next round (the full admission ladder applies — an upload is delivery, never trust); remove… — retire the collection's TOML (renamed aside, restorable) while its manifest, index and vectors stay on disk untouched. Removing the synthesized default collection (a node that never declared a TOML) switches the node to TOML mode with zero collections; a node can have none. Create and remove both take effect live — the worker hot-reloads collections every round.

Acquisition, profiles & licenses

In short: a profile says how much of a source to fetch; a license gate stands before the first byte; everything downloads through one shared bandwidth budget.

Collections can fetch their own corpus (opt-in per collection). Sources have license classes; a yellow-class source requires a recorded acknowledgement of its terms (timestamp + hash of the terms text) before the first byte moves. All transfers draw from one node-wide bandwidth budget with an optional schedule — there are no per-tool rate limits, and the Network page's override is temporary by construction.

What a profile is

A profile is a named corpus-size preset defined by the source's acquisition spec — a filter (file patterns, max files, max bytes) with a size estimate. It controls how much of the source this node fetches and keeps; it changes nothing about processing. Every current source defines the same four:

profilemeaninggutenberg (est.)pubmed (est.)
demoa couple of files — proves the pipeline end-to-end in minutes ~2 MB (3 files)~5 MB (2 files)
startera useful small corpus 500 files / ~2 GB50 files / ~500 MB
recenta substantial slice 5,000 files / ~20 GB200 files / ~5 GB
fulleverything the source offers ~80 GB~150 GB

Changing it afterwards: yes, any time. Use the collection card's grow profile… button (it previews files/bytes/ETA as a dry run before fetching) or louise hold records fetch <name> --profile recent. Acquisition is resumable and only fetches what's missing, so growing demo → starter → full costs no re-downloading. Also update profile in the collection's TOML — that's what the worker's periodic acquisition maintains from then on. Switching to a smaller profile stops future fetching but never deletes files already on disk — pruning a corpus is a manual, deliberate act.

Not every source's profiles form a ladder. Gutenberg, PubMed and the Wikipedia dumps are incremental (demo ⊂ starter ⊂ full), and grow offers the current profile and larger. The pre-embedded corpus is additive: each profile is a language, they combine freely (profile = "tr,it,en"), and grow is a checklist where what you already hold stays checked and checking another adds it rather than replacing it. A source may also be exclusive: each profile an alternative that never combines with another (a second would mint the same document ids), so grow offers nothing. Hand-populated collections (acquire_enabled = false) ignore profiles entirely; the Library card shows theirs as (hand-populated).

Fetching from peers, and seeding

The create panel's Acquisition drop-down offers three sources: off (hand-populated — you fill the corpus folder), from the source (the origin: rsync/https/hf-hub as the plugin declares), or from peers: paste a magnet URI or a .torrent path and the SAME acquisition engine fetches the corpus over BitTorrent — same profiles and filters, same license gate, same disk preflight; the torrent's own piece hashes replace the origin's checksum sidecars. Stored as peer_source in the collection's TOML. Without peer discovery (not built) the magnet carries a direct-peer hint, &x.pe=host:port.

Seeding is the other direction: louise share <collection> records that it is shared; from then on the worker seeds it whenever the node runs, is in download/seeding only, or seeding only — pause stands it down. Every uploaded byte is credited to the Network page's seeding class, and its Seeding table lists what is served, to how many peers, and how much has gone out. Deleting the .torrent file stops seeding. --subdir matters for layout: the hashed directory's name becomes the torrent root, so a peer's corpus_dir/<subdir>/… lands exactly where the plugin expects it (the pre-embedded corpus lives under data/).

The offer (04 §4.2): the Library's Offered by peers lists the collections live neighbours announce and this node does not hold — its catalogue minus what it holds — with each one's plugin, licence class and the peers serving it. take… is louise share fetch <collection id> queued for the worker: the Codex and its snapshots are pulled and verified, the collection is held with the slices and kinds you chose, and its records (and, if asked, the bundles peers accepted) follow at the worker's next fetch beat; a yellow or red collection then asks for its acknowledgement before any member moves. A peer chooses what it fetches; nothing is fetched that was not chosen. louise share offer prints the same list.

Extra formats (local only)

Some sources publish the same documents in more than one format. Louise needs exactly one of them — for Gutenberg that is the plain .txt, which is what gets cleaned, chunked, indexed and embedded. The others (for Gutenberg: .epub, nice for an e-reader) are offered as extra formats: tick them when creating the collection or in grow profile…, and Louise downloads them from the corpus source into the same per-book folders, purely as a local convenience. Unticking one stops future fetching but never deletes files already on disk.

Policy — peers exchange only the data that fulfils Louise's purpose. Extra formats are a local download from the corpus source and are never part of the peer-to-peer exchange: not published in corpus torrents, not in snapshot manifests, not counted as possession material. They also never inflate the pipeline numbers — parsed/indexed/embedded see only Louise's own format.

Reading the stage labels. Every stage label on a Library card — fetched (data), parsed (rdf), indexed (lexical), embedded / pre-embedded (dense), fetched (vectors) — keeps a constant name and speaks its state through one color scheme: green completed; turquoise (the collection-name accent) running or in the scheduling pool — the worker is on it or will reach it on its own; orange runs only on-demand (a query triggers it); grey off or paused. For the fetch row, compressed data replaces data for container sources and +extras is appended when extra formats are opted in; the denominator is what the origin's listing held at pass start. A collection that also carries a pre-embedded vector archive shows it as a light-green sub-box with its own fetched (vectors) and pre-embedded (dense) rows (the latter over the archive's declared id range). The embed-mode knob stays in the main box, one per card, and the sub-box repeats no space badge: it is the same embedding space as the main box, because that is precisely what import admission verifies.

Reading the fetched counter. The card keeps it bare: fetched D_done/D_total (f_done/f_total) (+ e_done/e_total). The first pair is documents — the unit parsed/indexed use — for sources whose layout makes documents countable (one directory = one book); the plain parenthesized pair is the underlying files (gutenberg: text + RDF metadata, so roughly two per book). Container sources cannot know document counts before unpacking, so their single pair counts archives and the card says compressed containers. The (+ …) pair appears only with extras opted in and counts the extra-format files, kept apart precisely because they are not Louise data.

Configuration tiers

In short: three layers that never mix — who the node is (env), what you want (files), what is temporarily overridden (DB, gone at restart).

tierwheremeaning
1 — identityenvironment variables who this node is: paths, endpoints, ADMIN_TOKEN, NODE_KEY_PATH, pipeline versions. Set in the deployment (compose/app YAML).

Troubleshooting

In short: most "stuck" states are deliberate safety stops — find the symptom, the fix is next to it.

symptomlikely cause / fix
worker shows paused, nothing processes the control-table toggle — press start on the Library page.
event log: embedding PAUSED (backend-gate) the embedding endpoint stopped reproducing its baseline. Check what changed (image tag? model file? pooling flags?). Restore it, or accept the new backend by removing its baseline file (the next check records it afresh) and plan a re-embed.
process exits with BOOT VALIDATION FAILED the pinned embedding space mismatches current config (invariant: never mix spaces silently). Restore the previous config, or wipe the collection's Lance directory and re-embed under the new recipe.
401 on admin API calls missing/wrong X-Admin-Token header, or ADMIN_TOKEN unset on the node (fail-closed).
N not indexable on a Library card the source has no usable content for them — a Gutenberg entry with metadata but no text file, an upstream retraction. Retrying cannot change that (the next scan re-applies it), which is why they are counted apart from failures. Empty book directories are not documents at all: they are transfer stubs (rsync creates the directory, then copies only the files the profile matches) and are reported once per scan instead.
N blocked on a Library card documents that failed a stage or exhausted their retries — these are the ones "clear errors & retry" puts back in the pipeline.
a progress bar stops short of 100% the two counts above explain the gap; between them they account for every document no stage will pick up again.
embedding paused on a Library card the backend gate stopped this collection's encoder writes because the endpoint no longer reproduces its recorded baseline. Fix the endpoint, or accept the new backend deliberately by removing its baseline file — knowing existing vectors came from a different function.
a book answers with stale/odd passages ask with verify: true or POST its chunk ids to /api/verify — failed verification quarantines the producing key and re-queues honest re-embedding.
