What this is

In short: your node turns document collections into something you can search and ask questions about — and exchanges the expensive part (embeddings) with other nodes, checking everything it receives.

louise-rag is a peer-to-peer RAG platform: each node ingests document collections (Project Gutenberg, PubMed, …), indexes them lexically (tantivy FTS) and densely (embeddings in LanceDB), and answers questions over them with a local LLM. Nodes can exchange signed vector bundles so one node's GPU-hours serve many — with cryptographic verification instead of trust. Two processes run per node: the web process (this UI, the JSON API, the OpenAI-compatible endpoint) and the worker (ingestion pipeline). Both operate on the same SQLite manifest and Lance vector store; state never travels, vectors do.

Ingestion pipeline

In short: every document climbs four steps — found, described, searchable, embedded — and any step can be safely interrupted and re-run.

Per document, in order: discover (corpus scan; also at startup and every DISCOVER_INTERVAL_MIN) → rdf (metadata) → fts (chunking, lexical index, entity tagging) → embed (dense vectors, when the embed mode says so). Every write is delete-then-insert keyed on the document uid, so any stage can be interrupted and re-run safely; a worker stop (SIGTERM) finishes the current document, commits, and exits cleanly. Each stage carries a version (CHUNK_VERSION, FTS_VERSION, ENTITY_VERSION, EMBED_VERSION); bumping one re-processes exactly the documents behind it — never silently.

Scope & embed modes

In short: scope decides which documents are in play; embed mode decides how much encoder time they get.

The scope (languages, explicit ids, caps) decides which documents are in play. The embed mode decides encoder spending: off — never embed; on-demand — embed only what queries actually touch (a priority queue fed by search misses; stored as "lazy" in the TOML and API, kept for compatibility); all — background-backfill everything in scope. The priority queue always outranks the backfill, so a user-requested document embeds first. Set the mode via POST /api/scope (see HTTP API).

What the mode actually controls

The knob touches one thing only: local encoder spending on dense vectors. Fetching, parsing and indexing never depend on it — they follow the node-wide worker state. Archive import (pre-embedded data) never depends on it either — it runs whenever the worker runs.

operationoffon-demand / fix on demandall / fix
fetched (acquisition) runs regardless — governed only by the node-wide worker state (run everything and download only fetch; pause stops it)
parsed (rdf) runs regardless under run everything; stands down under download only and pause
indexed (lexical) same as parsed — never gated by the embed mode
embedded (dense) — no archive never embeds; documents stay without vectors embeds only documents queries actually touch (the priority queue); no background work background-backfills everything in scope, queue first
embedded (dense) — pre-embedded archive declared the archive imports anyway (it is free); what it cannot cover stays without vectors (and post-quarantine re-embeds never run) the archive imports anyway; the encoder embeds only what a query touches the archive imports anyway and goes first; the encoder background-embeds only the documents the archive cannot cover — outside its declared id ranges, or left uncovered once an archive file is complete

The Library's embed-mode control is persistent: it writes embed_mode = "off" | "lazy" | "all" into collections/<name>.toml (Tier-2 desired state, the same way collection-create and the license ack write it) and applies immediately — it survives restarts. A runtime-only override is still possible via POST /api/scope; that one lasts until the worker next applies the TOML. A collection whose TOML is silent defaults to on-demand (stored value lazy). A collection with a pre-embedded archive has the same knob with the same three values — one knob, not two. The archive imports in every mode (it costs no encoder time and always goes first); the mode says what the local encoder does with the rest. Under all it embeds only what the archive cannot cover: documents outside the archive's declared id ranges (PubMed articles newer than the MedCPT snapshot, ~3M of 40M) and, once an archive file is complete, the few inside its range the archive did not hold (no abstract, a chunk-shape mismatch). Until that file is complete those wait for it — never a duplicate, never a wrong import. off leaves the uncovered documents without dense vectors — and note that after a quarantine, off also means the affected documents are never re-embedded.

Node-wide, the Library page offers three modes. run everything is the normal state. download only keeps acquisition and discovery going while parse, index and embed stand down — the two halves cost very differently, and this is the switch for when the node's heat or CPU matters more than its progress. Per-collection embed modes are left untouched, so switching back restores exactly what each collection was doing. pause stops everything, including starting new fetches.

Each Library card names which processor that spending lands on — GPU for a collection served by the shared GPU encoder (one collection at a time, serial by design) and CPU for one served by a CPU encoder container, which runs beside the GPU without competing for it. Declare it explicitly with device = "gpu"|"cpu" in the collection's [embed] block; otherwise it is inferred from concurrency. The device is descriptive only and never part of the embedding space — the same model on a different device computes the same function.

Under all, the card reports the dense backfill still awaiting the encoder rather than the on-demand queue, which is empty by definition in that mode: backfill selects straight from the manifest and never touches the queue.

Embedding safety

In short: two vectors are only comparable when the exact same machinery produced them — everything in this section defends that one rule.

Vectors are only comparable inside one embedding space: same model weights, dtype, normalization, pooling, chunking and cleaning versions. The space is pinned per collection at first boot and checked on every boot — a confirmed mismatch refuses to boot rather than silently mixing spaces.

Because an HTTP embedding endpoint can change behind a stable name, the worker additionally runs a behavioral backend gate: on first use it embeds fixed probe texts and records the vectors; before writing any new vectors it re-embeds the probes and requires cosine ≥ 0.995 against that baseline. If the endpoint stops reproducing itself (model swap, build change, pooling change), embedding pauses — documents are never marked errored, search and lexical indexing continue — until an operator fixes the endpoint or accepts the new backend with backend rebaseline (which implies re-embedding).

EMBED_BATCH=1 is load-bearing. llama-server corrupts long sequences when a single embeddings request carries multiple texts (verified live 2026-08-17: batch-of-8 → cosine 0.32 against the same text embedded alone), and its prompt cache can replay corrupted results afterwards. Parallel single-text requests are verified safe — use EMBED_CONCURRENCY for throughput, never EMBED_BATCH. Also pin the embedding server's image by digest: a moving tag is how a backend changes identity silently.

Bundles & the P2P plane

In short: nodes share finished embeddings so one GPU serves many — and every import is checked, never trusted.

A bundle is a signed, portable set of vectors: header + Parquet vectors + per-document possession hashes, Ed25519-signed by the producing node's key. Importing one lets a document reach embedded without local GPU work. Every import passes admission checks regardless of who signed it (structure, isotropy, chunk-overlap invariant, sample re-embedding, degenerate-vector detection), producer keys are trusted on first use and quarantinable, and imported chunks can be verified on use — each verification is permanent per chunk. The verification ladder (T0 structural → T3 spot recompute against the local model) records evidence for every decision, and bundle resweep re-checks earlier imports after a trust or calibration change.

What travels, what stays local

The dividing rule: a peer shares what is expensive to make and cheap to verify, and recomputes what is the reverse.

artifacttravels?why
corpus bytesyes (torrents, mirrors) expensive to move from origin, trivially verified by hash.
vectorsyes (signed bundles, genesis archives) the GPU-hours are the whole cost; verifiable by sampled re-embedding against the local encoder.
corpus enumeration (which documents exist in a snapshot)designed, not built discovery over millions of files is slow and every peer repeats it identically — a signed listing in the snapshot manifest would let a peer skip it and still verify what lands. The plan is recorded; no wire format exists yet.
FTS indexno — deliberately cheap to recompute locally (~1 ms/doc), expensive to verify received (the only check is rebuilding it, which costs the recompute anyway), and coupled to local versions and config — a shared index would import another node's chunking decisions unverifiably.
SQLite state (manifest, progress, settings) never it describes this node's pipeline position and choices; on any other node it is meaningless or wrong.
extra formats (e.g. epubs)never local convenience only — peers exchange the data that fulfils Louise's purpose (see Acquisition → Extra formats).

Reusing published embeddings (genesis import)

In short: when someone already paid the GPU-hours for a corpus, this node reuses their vectors — after checking they came from the same encoder.

If someone already paid the GPU-hours for a corpus, this node reuses that work instead of re-embedding: NCBI publishes MedCPT vectors for essentially all of PubMed (public domain), and any third party can publish a compatible dataset. The import is admission, not trust: only documents this node actually holds receive vectors; every vector is converted (f32→f16, L2-normalized) on the way in; and a sample is re-encoded through the collection's own [embed] endpoint — if the archive was not produced by the same function, the shard is refused whole, however well-formed. Provenance is ledgered per shard, imports resume mid-archive, and the worker gap-fills whatever the archive lacks (newer documents) through the same endpoint, so the space stays coherent forever.

Default-on. A collection whose TOML declares genesis_archive = "medcpt-pubmed" (written automatically by the create dialog when the plugin has a known archive; delete the line to opt out) is drained by the worker on its own — one shard per round, before any local GPU embedding — and the Library card shows the coverage. An archive is split by its producer into numbered archive files ("shards": NCBI publishes MedCPT's vectors as 37 files of ~3 GB; the pre-embedded Wikipedia corpus IS its 1,447 parquet files). A remote archive is a second download stream of the collection, beside the corpus fetch and behind it on the link (the corpus wins: without it the vectors are useless — that is the archive class of the bandwidth budget). Files land a few at a time (a bounded cache on disk, GENESIS_CACHE_BYTES, and a disk preflight), and each one applies as soon as it lands for the documents already indexed, is revisited as more of them clear indexing (a revisit that finds nothing backs off, per file), and is deleted once nothing in its id range still waits. MedCPT's files are exact PMID ranges (file i = PMIDs i·10⁶ …), so the worker knows from the id alone which documents the archive can cover — the local encoder never spends a GPU-hour on one. A local archive is read file by file as its documents pass indexing. The CLI does the same thing on demand:

Why some pre-embedded data is combined with a collection and some stands alone. The rule follows what the data is. Pre-embedded data that is a corpus in its own right — text and vectors together, like the wikivec parquet files — stands alone as its own collection, with its own documents, ids and embedding space. Pre-embedded data that is vectors for another collection's documents — MedCPT for pubmed: same document ids, no text of its own, computed in the very space the collection is pinned to — must live inside that collection, shown as the light-green sub-box on its Library card. Split out, it would be a "collection" owning vectors but no documents: it could not search lexically, could not verify possession (hashes bind to document bytes it would not have), and retrieval would double-count the same documents across two fused legs. So: corpus-with-vectors → own card; vectors-for-your-documents → sub-box. 

# NCBI MedCPT vectors into the pubmed collection (resumable):
python -m app.cli genesis import pubmed --archive medcpt-pubmed

# any compatible dataset: a parquet of (id, vector) rows
python -m app.cli genesis import <collection> --parquet /path/data.parquet \
    --uid-prefix "pubmed:" --archive-id "my-dataset-v1"

python -m app.cli genesis status <collection>

This cuts both ways: a collection filled from a genesis archive (or embedded locally) can be exported as a signed bundle from its Library card — publishing embeddings other nodes (and other projects) can verify and reuse is exactly how a platform earns visibility. The per-collection encoder setup for MedCPT (two small CPU containers) is documented in deploy/truenas-medcpt-embed.yaml.

Adding a collection

In short: a collection is one corpus in one embedding space, defined by one TOML file — the create dialog writes it for you.

A collection is defined by one versioned TOML file — that file existing is what makes the collection exist (config tier 2, never a database write). The workflow:

1. Draft it. On the Library page, use the Add a collection panel: pick a name, a plugin (gutenberg, pubmed, wikipedia, or genome — reference assemblies as chromosome documents with deterministic sequence windows; its profiles are assemblies: demo = yeast, starter = + fly, full = + human GRCh38), a profile, and optionally a dedicated corpus folder. Preview shows the source's license class (and terms text, if acknowledgement is required) plus the exact TOML; Create on this node writes that TOML for you, with per-collection data paths already isolated.

Dedicated corpus folders (TrueNAS). Corpus datasets are mapped under one well-known root inside the container, /corpora (env CORPUS_MOUNTS_DIR) — you never type arbitrary container paths. Create the dataset on the host, edit the louise-rag app, and add to both services (web and worker): 

volumes:
  - /mnt/tank/data/pubmed:/corpora/pubmed        # example: rw, platform acquires into it
  - /mnt/<pool>/<dataset>:/corpora/<name>:ro    # ro when an external process feeds it
  ...

Saving the edit restarts the app with the mount; the folder then appears in the create dialog's corpus dropdown. A folder already claimed by another collection is shown but not selectable — one corpus, one collection.

2. (By hand, alternatively) save it yourself as collections/<name>.toml under the node's CONFIG_DIR (on this deployment: /mnt/ssd4/apps/louise-rag/config/collections/), and commit it if the config is versioned. A minimal file: 

plugin = "pubmed"
profile = "demo"
acquire_enabled = true            # omit for a hand-populated corpus
# license_ack = "<from corpus add --ack-terms>"   # yellow-class sources only

corpus_dir = "/corpus-pubmed"     # where the documents live (or will land)
[paths]                           # REQUIRED for a second collection:
manifest = "/data/pubmed/manifest.db"   # defaults point at the first
fts      = "/data/pubmed/fts"           # collection's paths — never share
lancedb  = "/data/pubmed/lancedb"       # a manifest or vector table

3. It goes live on its own — the web pages read collections per request, and the worker hot-reloads them each round: a created collection starts discovering within seconds, no restart. It appears on the Library page and in Ask's collection chips; its embedding space is pinned on first contact.

4. Fill it. Either point corpus_dir at documents you already have (the worker discovers them on its next scan), or — with acquire_enabled = true — fetch from the source: python -m app.cli corpus add <name> --profile demo --dry-run to see size/ETA, then without --dry-run to run. A yellow-class source refuses to fetch until its terms are acknowledged (corpus add <name> --ack-terms <terms-file> prints the license_ack line for the TOML). Then grow it later with corpus grow <name> --profile full or the Library page's grow profile… button.

Managing it. Each collection card also offers: export bundle — download this collection's vectors as a signed bundle (tar.gz) another node can import; import bundle… — upload a bundle into the collection's inbox, where the worker verifies and imports it next round (the full admission ladder applies — an upload is delivery, never trust); remove… — retire the collection's TOML (renamed aside, restorable) while its manifest, index and vectors stay on disk untouched. Removing the synthesized default collection isn't possible from the UI. Create and remove both take effect live — the worker hot-reloads collections every round.

Acquisition, profiles & licenses

In short: a profile says how much of a source to fetch; a license gate stands before the first byte; everything downloads through one shared bandwidth budget.

Collections can fetch their own corpus (opt-in per collection). Sources have license classes; a yellow-class source requires a recorded acknowledgement of its terms (timestamp + hash of the terms text) before the first byte moves. All transfers draw from one node-wide bandwidth budget with an optional schedule — there are no per-tool rate limits, and the Network page's override is temporary by construction.

What a profile is

A profile is a named corpus-size preset defined by the source's acquisition spec — a filter (file patterns, max files, max bytes) with a size estimate. It controls how much of the source this node fetches and keeps; it changes nothing about processing. Every current source defines the same four:

profilemeaninggutenberg (est.)pubmed (est.)
demoa couple of files — proves the pipeline end-to-end in minutes ~2 MB (3 files)~5 MB (2 files)
startera useful small corpus 500 files / ~2 GB50 files / ~500 MB
recenta substantial slice 5,000 files / ~20 GB200 files / ~5 GB
fulleverything the source offers ~80 GB~150 GB

Changing it afterwards: yes, any time. Use the collection card's grow profile… button (it previews files/bytes/ETA as a dry run before fetching) or corpus grow <name> --profile recent. Acquisition is resumable and only fetches what's missing, so growing demo → starter → full costs no re-downloading. Also update profile in the collection's TOML — that's what the worker's periodic acquisition maintains from then on. Switching to a smaller profile stops future fetching but never deletes files already on disk — pruning a corpus is a manual, deliberate act.

Not every source's profiles form a ladder. Gutenberg, PubMed and the Wikipedia dumps are incremental (demo ⊂ starter ⊂ full), and grow offers the current profile and larger. The pre-embedded corpus is additive: each profile is a language, they combine freely (profile = "tr,it,en"), and grow is a checklist where what you already hold stays checked and checking another adds it rather than replacing it. A genome collection is exclusive: each profile is an assembly, one collection holds exactly one assembly (§9), and grow therefore offers nothing — a second assembly is a second collection, because document ids are per-FASTA record ordinals and two assemblies in one corpus would overwrite each other. Hand-populated collections (acquire_enabled = false) ignore profiles entirely; the Library card shows theirs as (hand-populated).

Fetching from peers, and seeding

The create panel's Acquisition drop-down offers three sources: off (hand-populated — you fill the corpus folder), from the source (the origin: rsync/https/hf-hub as the plugin declares), or from peers: paste a magnet URI or a .torrent path and the SAME acquisition engine fetches the corpus over BitTorrent — same profiles and filters, same license gate, same disk preflight; the torrent's own piece hashes replace the origin's checksum sidecars. Stored as peer_source in the collection's TOML. Without peer discovery (not built) the magnet carries a direct-peer hint, &x.pe=host:port, which torrent publish --peer-hint prints for you.

Seeding is the other direction: torrent publish <collection> [--subdir data] hashes the corpus (minutes on a large one) and records it; from then on the worker seeds it whenever the node runs, is in download/seeding only, or seeding only — pause stands it down. Every uploaded byte is credited to the Network page's seeding class, and its Seeding table lists what is served, to how many peers, and how much has gone out. Deleting the .torrent file stops seeding. --subdir matters for layout: the hashed directory's name becomes the torrent root, so a peer's corpus_dir/<subdir>/… lands exactly where the plugin expects it (the pre-embedded corpus lives under data/).

Extra formats (local only)

Some sources publish the same documents in more than one format. Louise needs exactly one of them — for Gutenberg that is the plain .txt, which is what gets cleaned, chunked, indexed and embedded. The others (for Gutenberg: .epub, nice for an e-reader) are offered as extra formats: tick them when creating the collection or in grow profile…, and Louise downloads them from the corpus source into the same per-book folders, purely as a local convenience. Unticking one stops future fetching but never deletes files already on disk.

Policy — peers exchange only the data that fulfils Louise's purpose. Extra formats are a local download from the corpus source and are never part of the peer-to-peer exchange: not published in corpus torrents, not in snapshot manifests, not counted as possession material. They also never inflate the pipeline numbers — parsed/indexed/embedded see only Louise's own format.

Reading the stage labels. Every stage label on a Library card — fetched (data), parsed (rdf), indexed (lexical), embedded / pre-embedded (dense), fetched (vectors) — keeps a constant name and speaks its state through one color scheme: green completed; turquoise (the collection-name accent) running or in the scheduling pool — the worker is on it or will reach it on its own; orange runs only on-demand (a query triggers it); grey off or paused. For the fetch row, compressed data replaces data for container sources and +extras is appended when extra formats are opted in; the denominator is what the origin's listing held at pass start. A collection that also carries a pre-embedded vector archive shows it as a light-green sub-box with its own fetched (vectors) and pre-embedded (dense) rows and the local gap-fill knob — same embedding space as the main box (its space badge repeats it), because that is precisely what import admission verifies.

Reading the fetched counter. The card keeps it bare: fetched D_done/D_total (f_done/f_total) (+ e_done/e_total). The first pair is documents — the unit parsed/indexed use — for sources whose layout makes documents countable (one directory = one book); the plain parenthesized pair is the underlying files (gutenberg: text + RDF metadata, so roughly two per book). Container sources cannot know document counts before unpacking, so their single pair counts archives and the card says compressed containers. The (+ …) pair appears only with extras opted in and counts the extra-format files, kept apart precisely because they are not Louise data.

Troubleshooting

In short: most "stuck" states are deliberate safety stops — find the symptom, the fix is next to it.

symptomlikely cause / fix
worker shows paused, nothing processes the control-table toggle — press start on the Library page.
event log: embedding PAUSED (backend-gate) the embedding endpoint stopped reproducing its baseline. Check what changed (image tag? model file? pooling flags?). Restore it, or accept the new backend with backend rebaseline --yes and plan a re-embed.
process exits with BOOT VALIDATION FAILED the pinned embedding space mismatches current config (invariant: never mix spaces silently). Restore the previous config, or wipe the collection's Lance directory and re-embed under the new recipe.
401 on admin API calls missing/wrong X-Admin-Token header, or ADMIN_TOKEN unset on the node (fail-closed).
N not indexable on a Library card the source has no usable content for them — a Gutenberg entry with metadata but no text file, an upstream retraction. Retrying cannot change that (the next scan re-applies it), which is why they are counted apart from failures. Empty book directories are not documents at all: they are transfer stubs (rsync creates the directory, then copies only the files the profile matches) and are reported once per scan instead.
