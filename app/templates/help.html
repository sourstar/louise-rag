What this is

louise-rag is a peer-to-peer RAG platform: each node ingests document collections (Project Gutenberg, PubMed, …), indexes them lexically (tantivy FTS) and densely (embeddings in LanceDB), and answers questions over them with a local LLM. Nodes can exchange signed vector bundles so one node's GPU-hours serve many — with cryptographic verification instead of trust. Two processes run per node: the web process (this UI, the JSON API, the OpenAI-compatible endpoint) and the worker (ingestion pipeline). Both operate on the same SQLite manifest and Lance vector store; state never travels, vectors do.

Admin pages need the node's ADMIN_TOKEN (an environment variable set at install). Enter it once at /admin/login — a 30-day cookie keeps the browser session authenticated. If the token is unset, admin areas are locked entirely (fail-closed); Ask keeps working regardless. Navigating to an admin page without a session simply brings you to the login form and returns you afterwards.

Ingestion pipeline

Per document, in order: discover (corpus scan; also at startup and every DISCOVER_INTERVAL_MIN) → rdf (metadata) → fts (chunking, lexical index, entity tagging) → embed (dense vectors, when the embed mode says so). Every write is delete-then-insert keyed on the document uid, so any stage can be interrupted and re-run safely; a worker stop (SIGTERM) finishes the current document, commits, and exits cleanly. Each stage carries a version (CHUNK_VERSION, FTS_VERSION, ENTITY_VERSION, EMBED_VERSION); bumping one re-processes exactly the documents behind it — never silently.

Scope & embed modes

The scope (languages, explicit ids, caps) decides which documents are in play. The embed mode decides GPU spending: off — never embed; lazy — embed only what queries actually touch (a priority queue fed by search misses); all — background- backfill everything in scope. The priority queue always outranks the backfill, so a user-requested document embeds first. Set the mode via POST /api/scope (see HTTP API).

Embedding safety

Vectors are only comparable inside one embedding space: same model weights, dtype, normalization, pooling, chunking and cleaning versions. The space is pinned per collection at first boot and checked on every boot — a confirmed mismatch refuses to boot rather than silently mixing spaces.

Because an HTTP embedding endpoint can change behind a stable name, the worker additionally runs a behavioral backend gate: on first use it embeds fixed probe texts and records the vectors; before writing any new vectors it re-embeds the probes and requires cosine ≥ 0.995 against that baseline. If the endpoint stops reproducing itself (model swap, build change, pooling change), embedding pauses — documents are never marked errored, search and lexical indexing continue — until an operator fixes the endpoint or accepts the new backend with backend rebaseline (which implies re-embedding).

EMBED_BATCH=1 is load-bearing. llama-server corrupts long sequences when a single embeddings request carries multiple texts (verified live 2026-08-17: batch-of-8 → cosine 0.32 against the same text embedded alone), and its prompt cache can replay corrupted results afterwards. Parallel single-text requests are verified safe — use EMBED_CONCURRENCY for throughput, never EMBED_BATCH. Also pin the embedding server's image by digest: a moving tag is how a backend changes identity silently.

Bundles & the P2P plane

A bundle is a signed, portable set of vectors: header + Parquet vectors + per-document possession hashes, Ed25519-signed by the producing node's key. Importing one lets a document reach embedded without local GPU work. Every import passes admission checks regardless of who signed it (structure, isotropy, chunk-overlap invariant, sample re-embedding, degenerate-vector detection), producer keys are trusted on first use and quarantinable, and imported chunks can be verified on use — each verification is permanent per chunk. The verification ladder (T0 structural → T3 spot recompute against the local model) records evidence for every decision, and bundle resweep re-checks earlier imports after a trust or calibration change.

Reusing published embeddings (genesis import)

If someone already paid the GPU-hours for a corpus, this node reuses that work instead of re-embedding: NCBI publishes MedCPT vectors for essentially all of PubMed (public domain), and any third party can publish a compatible dataset. The import is admission, not trust: only documents this node actually holds receive vectors; every vector is converted (f32→f16, L2-normalized) on the way in; and a sample is re-encoded through the collection's own [embed] endpoint — if the archive was not produced by the same function, the shard is refused whole, however well-formed. Provenance is ledgered per shard, imports resume mid-archive, and the worker gap-fills whatever the archive lacks (newer documents) through the same endpoint, so the space stays coherent forever. 

# NCBI MedCPT vectors into the pubmed collection (resumable):
python -m app.cli genesis import pubmed --archive medcpt-pubmed

# any compatible dataset: a parquet of (id, vector) rows
python -m app.cli genesis import <collection> --parquet /path/data.parquet \
    --uid-prefix "pubmed:" --archive-id "my-dataset-v1"

python -m app.cli genesis status <collection>

This cuts both ways: a collection filled from a genesis archive (or embedded locally) can be exported as a signed bundle from its Library card — publishing embeddings other nodes (and other projects) can verify and reuse is exactly how a platform earns visibility. The per-collection encoder setup for MedCPT (two small CPU containers) is documented in deploy/truenas-medcpt.yaml.

Adding a collection

A collection is defined by one versioned TOML file — that file existing is what makes the collection exist (config tier 2, never a database write). The workflow:

1. Draft it. On the Library page, use the Add a collection panel: pick a name, a plugin (e.g. gutenberg, pubmed), a profile, and optionally a dedicated corpus folder (a container path like /corpus-pubmed). Preview shows the source's license class (and terms text, if acknowledgement is required) plus the exact TOML; Create on this node writes that TOML for you, with per-collection data paths already isolated.

Dedicated corpus folders (TrueNAS). Corpus datasets are mapped under one well-known root inside the container, /corpora (env CORPUS_MOUNTS_DIR) — you never type arbitrary container paths. Create the dataset on the host, edit the louise-rag app, and add to both services (web and worker): 

volumes:
  - /mnt/tank/data/pubmed:/corpora/pubmed        # example: rw, platform acquires into it
  - /mnt/<pool>/<dataset>:/corpora/<name>:ro    # ro when an external process feeds it
  ...

Saving the edit restarts the app with the mount; the folder then appears in the create dialog's corpus dropdown. A folder already claimed by another collection is shown but not selectable — one corpus, one collection.

2. (By hand, alternatively) save it yourself as collections/<name>.toml under the node's CONFIG_DIR (on this deployment: /mnt/ssd4/apps/louise-rag/config/collections/), and commit it if the config is versioned. A minimal file: 

plugin = "pubmed"
profile = "demo"
acquire_enabled = true            # omit for a hand-populated corpus
# license_ack = "<from corpus add --ack-terms>"   # yellow-class sources only

corpus_dir = "/corpus-pubmed"     # where the documents live (or will land)
[paths]                           # REQUIRED for a second collection:
manifest = "/data/pubmed/manifest.db"   # defaults point at the first
fts      = "/data/pubmed/fts"           # collection's paths — never share
lancedb  = "/data/pubmed/lancedb"       # a manifest or vector table

3. It goes live on its own — the web pages read collections per request, and the worker hot-reloads them each round: a created collection starts discovering within seconds, no restart. It appears on the Library page and in Ask's collection chips; its embedding space is pinned on first contact.

4. Fill it. Either point corpus_dir at documents you already have (the worker discovers them on its next scan), or — with acquire_enabled = true — fetch from the source: python -m app.cli corpus add <name> --profile demo --dry-run to see size/ETA, then without --dry-run to run. A yellow-class source refuses to fetch until its terms are acknowledged (corpus add <name> --ack-terms <terms-file> prints the license_ack line for the TOML). Then grow it later with corpus grow <name> --profile full or the Library page's grow profile… button.

Managing it. Each collection card also offers: export bundle — download this collection's vectors as a signed bundle (tar.gz) another node can import; import bundle… — upload a bundle into the collection's inbox, where the worker verifies and imports it next round (the full admission ladder applies — an upload is delivery, never trust); remove… — retire the collection's TOML (renamed aside, restorable) while its manifest, index and vectors stay on disk untouched. Removing the synthesized default collection isn't possible from the UI. Create and remove both take effect live — the worker hot-reloads collections every round.

Acquisition, profiles & licenses

Collections can fetch their own corpus (opt-in per collection). Sources have license classes; a yellow-class source requires a recorded acknowledgement of its terms (timestamp + hash of the terms text) before the first byte moves. All transfers draw from one node-wide bandwidth budget with an optional schedule — there are no per-tool rate limits, and the Network page's override is temporary by construction.

What a profile is

A profile is a named corpus-size preset defined by the source's acquisition spec — a filter (file patterns, max files, max bytes) with a size estimate. It controls how much of the source this node fetches and keeps; it changes nothing about processing. Every current source defines the same four:

profilemeaninggutenberg (est.)pubmed (est.)
demoa couple of files — proves the pipeline end-to-end in minutes ~2 MB (3 files)~5 MB (2 files)
startera useful small corpus 500 files / ~2 GB50 files / ~500 MB
recenta substantial slice 5,000 files / ~20 GB200 files / ~5 GB
fulleverything the source offers ~80 GB~150 GB

Changing it afterwards: yes, any time. Use the collection card's grow profile… button (it previews files/bytes/ETA as a dry run before fetching) or corpus grow <name> --profile recent. Acquisition is resumable and only fetches what's missing, so growing demo → starter → full costs no re-downloading. Also update profile in the collection's TOML — that's what the worker's periodic acquisition maintains from then on. Two honest caveats: profiles aren't ordered in the type system ("grow" names the intent, it doesn't enforce bigger-than-before), and switching to a smaller profile stops future fetching but never deletes files already on disk — pruning a corpus is a manual, deliberate act. Hand-populated collections (acquire_enabled = false) ignore profiles entirely; the Library card shows theirs as (hand-populated).

Troubleshooting

symptomlikely cause / fix
worker shows paused, nothing processes the control-table toggle — press start on the Library page.
event log: embedding PAUSED (backend-gate) the embedding endpoint stopped reproducing its baseline. Check what changed (image tag? model file? pooling flags?). Restore it, or accept the new backend with backend rebaseline --yes and plan a re-embed.
process exits with BOOT VALIDATION FAILED the pinned embedding space mismatches current config (invariant: never mix spaces silently). Restore the previous config, or wipe the collection's Lance directory and re-embed under the new recipe.
401 on admin API calls missing/wrong X-Admin-Token header, or ADMIN_TOKEN unset on the node (fail-closed).
documents with errors like missing txt corpus entries without a usable text file — counted, skipped, and harmless. "clear errors & retry" on the Library page re-attempts after a corpus update.
a book answers with stale/odd passages ask with verify: true or POST its chunk ids to /api/verify — failed verification quarantines the producing key and re-queues honest re-embedding.
