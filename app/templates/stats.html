Embedding

Document counts are cached for two minutes and refreshed in the background — the numbers below are {% if counts_age < 5 %}fresh{% else %}up to {{ '%.0f'|format(counts_age) }}s old{% endif %}. Each one is a full scan of that collection's documents table (24M rows for pubmed, ~12s), so computing them per page load made this page a 20-second wait. A backfill moves over days; a two-minute-old count does not mislead, but a count of unknown age would.
encoder is throughput measured inside the endpoint call — what the encoder is worth, independent of whether the worker had anything else to do. That is the column to compare a CPU encoder against a GPU one. duty is the share of elapsed time this collection actually held the encoder: embedding is GPU-serial across collections by doctrine, so a low duty means the encoder is fine and the collection is queueing. chars/s is the fair cross-collection figure — chunk sizes differ per collection (ctx column), so chunks/s alone would flatter a small-context encoder for doing less work per chunk. Both are shown: chunks/s is the intuitive one, chars/s is the one to compare on.

chunks left counts only chunks the pipeline already knows about. The count is written by the lexical-index stage, so a document that has not reached it yet contributes an unknown amount, shown separately rather than as zero — and any ETA beside one is a floor (≥), not an estimate. Blocked documents are excluded entirely until their errors are cleared.

ETA uses the wall-clock rate, not the encoder rate: the encoder is shared serially, so its raw speed would promise a finish time no collection can reach. Remaining work is counted in chunks, not documents — a genome contig and a PubMed abstract are not the same unit of work.

Reading this to choose hardware

The question this page exists to answer is whether a GPU version of an encoder is worth running. Compare chars/s between collections on the same endpoint kind before comparing across kinds, then check duty: an encoder at 20% duty is idle four fifths of the time, and making it faster changes nothing until the collections competing for it are also faster. The honest order is usually duty first, speed second.

Nothing here samples the model itself — these are end-to-end figures including HTTP and the chunk payload, which is what the pipeline actually experiences.
